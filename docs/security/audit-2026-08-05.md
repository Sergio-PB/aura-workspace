## Findings

### CRITICAL

#### C-1: Hardcoded JWT Secret Fallback

**File:** `apps/backend/src/middleware/auth.ts:7`  
**Finding:** `const SECRET_KEY = process.env.AURA_JWT_SECRET || "aura-dev-secret-change-in-production";`

The server starts with a well-known default secret if `AURA_JWT_SECRET` is not set. `serve.ts:9-13` only logs a warning — it does not refuse to start. Anyone who knows this default can forge valid JWTs for any user.

**Fix:** Remove the fallback. Crash on startup if `AURA_JWT_SECRET` is missing. Generate a random secret in dev mode only.

```ts
const SECRET_KEY = process.env.AURA_JWT_SECRET;
if (!SECRET_KEY) {
  if (process.env.NODE_ENV === "development") {
    // Generate a random secret for local dev
    const randomBytes = crypto.getRandomValues(new Uint8Array(32));
    SECRET_KEY = Array.from(randomBytes).map(b => b.toString(16).padStart(2, "0")).join("");
    console.warn("[startup] Generated random JWT secret for dev. Set AURA_JWT_SECRET in production.");
  } else {
    throw new Error("AURA_JWT_SECRET is required in production");
  }
}
```

### HIGH

#### H-1: No Authentication on WebSocket Connections

**File:** `apps/backend/src/index.ts:48-49`  
**Finding:** The WebSocket upgrade endpoint has no authentication. The comment says "ponytail: no auth on WS upgrade; clients send userId as first message." Any client can connect and claim any `userId`. The `move_tick` handler trusts `userId` and `targetUserId` from the client without verification.

**Impact:** An attacker can:
- Spoof move ticks for any user, inflating their aura points
- Subscribe to any user's feed by claiming their userId
- Flood the leaderboard with fake data

**Fix:** Require a valid JWT as a query parameter on the WS upgrade, or validate the first message contains a signed challenge. At minimum, validate that `userId` in move_tick messages matches the authenticated WS connection.

#### H-2: No fromUserId Verification on Attribution Creation

**File:** `apps/backend/src/routes/attributions.ts:28-87`  
**Finding:** The `POST /attributions` route is protected by `authMiddleware` (which sets `c.get("userId")`), but the handler never checks that `data.fromUserId` matches the authenticated user. Anyone with a valid JWT can create attributions as any user.

**Impact:** An attacker can attribute points from any user to any other user, bypassing the anti-gaming and rate-limit checks (which use the authenticated userId, not the body's fromUserId).

**Fix:** Add a check at the top of the handler:
```ts
const authUserId = c.get("userId");
if (data.fromUserId !== authUserId) {
  return c.json({ ok: false, error: { code: "FORBIDDEN", message: "fromUserId must match authenticated user" } }, 403);
}
```

#### H-3: Public Routes Accept Arbitrary User IDs

**Files:**
- `apps/backend/src/routes/events.ts:28` — `createdBy` from body, no auth verification
- `apps/backend/src/routes/recordings.ts:32` — `recordedBy` from body, no auth verification
- `apps/backend/src/routes/events.ts:60` — `userId` from body on join, no auth verification

**Finding:** These POST endpoints are public (no `authMiddleware` applied in `index.ts`). They accept user IDs from the request body without verifying the caller owns that identity.

**Impact:** Anyone can create events and recordings as any user, join events as any user.

**Fix:** Either apply `authMiddleware` to these routes and verify the body's user ID matches the token, or require a signed payload from the client.

### MEDIUM

#### M-1: No CORS Origin Restrictions

**File:** `apps/backend/src/index.ts:34`  
**Finding:** `app.use("*", cors())` — CORS is enabled for all origins with default settings. Any website can make authenticated requests to the API.

**Fix:** Restrict to known origins in production:
```ts
app.use("*", cors({
  origin: process.env.NODE_ENV === "production" 
    ? ["https://ifarm.club", "https://app.ifarm.club"] 
    : "*"
}));
```

#### M-2: No Input Sanitization on Display Names

**Files:** `apps/backend/src/routes/auth.ts:18`, `apps/backend/src/db/schema.ts:11`  
**Finding:** `displayName` is validated for length (1-100 chars) but not sanitized for HTML/script content. If the frontend renders display names without escaping, this is a stored XSS vector.

**Fix:** Either sanitize on input (strip HTML tags) or ensure the frontend always escapes. Both is better. Add a Zod transform:
```ts
displayName: z.string().min(1).max(100).transform(s => s.replace(/[<>]/g, ""))
```

#### M-3: No Rate Limiting on Public Routes

**Files:** `apps/backend/src/index.ts:79-92`  
**Finding:** Rate limiting is only applied to `/attributions/*` and `/validations/*`. Public routes (`/events`, `/recordings`, `/feed`, `/users`, `/auth`) have no rate limiting.

**Impact:** An attacker can:
- Flood `/auth/register` to exhaust the challenge store memory
- Flood `/feed` to cause expensive DB queries
- Flood `/events` or `/recordings` to spam the database

**Fix:** Apply `rateLimit()` to all public POST endpoints. Consider a stricter limit for `/auth/*`.

#### M-4: WebSocket Message Trust Without Validation

**File:** `apps/backend/src/index.ts:56-70`  
**Finding:** The WS message handler parses JSON and trusts `parsed.type === "move_tick"` to call `handleMoveTick`. There's no Zod validation of the move_tick message shape. Malformed messages could cause runtime errors or unexpected behavior.

**Fix:** Validate move_tick messages with Zod before passing to `handleMoveTick`.

### LOW

#### L-1: Challenge Store in Memory (Lost on Restart)

**File:** `apps/backend/src/routes/auth.ts:27`  
**Finding:** `const challenges = new Map()` — challenge nonces are stored in memory. On server restart, all pending login attempts fail. Users must re-register to get a new challenge.

**Fix:** Acceptable for MVP. Move to DB or Redis before production.

#### L-2: No Token Refresh Mechanism

**File:** `apps/backend/src/middleware/auth.ts:40`  
**Finding:** Tokens expire after 24 hours with no refresh mechanism. If a token is stolen, it's valid for up to 24 hours.

**Fix:** Add refresh tokens (stored in DB, revocable) or reduce token TTL to 1 hour with sliding expiration.

#### L-3: No JWT Key Rotation

**File:** `apps/backend/src/middleware/auth.ts:7`  
**Finding:** The JWT secret is static. If compromised, all tokens are compromised until the secret is rotated (which invalidates all existing sessions).

**Fix:** Acceptable for MVP. Add key rotation with a key ID in the JWT header before production.

#### L-4: No Security Headers

**File:** `apps/backend/src/index.ts`  
**Finding:** No Content-Security-Policy, X-Content-Type-Options, X-Frame-Options, or Strict-Transport-Security headers are set.

**Fix:** Add a middleware that sets basic security headers:
```ts
app.use("*", async (c, next) => {
  c.res.headers.set("X-Content-Type-Options", "nosniff");
  c.res.headers.set("X-Frame-Options", "DENY");
  c.res.headers.set("Strict-Transport-Security", "max-age=31536000; includeSubDomains");
  await next();
});
```

## What's Good

- **Ed25519 auth** — cryptographic keypairs, no passwords to leak. Challenge-response login is solid.
- **Zod validation on all POST routes** — input shapes are validated. Just missing the auth-user-matches-body-user check.
- **Anti-gaming middleware** — point velocity, new account limits, Sybil IP detection, reciprocal farming detection. Comprehensive for MVP.
- **Rate limiting** — sliding window, configurable, with cleanup. Applied where it matters most.
- **Soft-delete with audit log** — GDPR-friendly data handling.
- **SQL parameterization via Drizzle** — no SQL injection risk.
- **No hardcoded secrets in code** (except the JWT fallback) — AWS keys come from env vars.
